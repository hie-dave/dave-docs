Repository Map

This page gives a practical tour of the LPJ-GUESS DAVE repository. It is written for people who need to run simulations, inspect inputs, or make small configuration changes without first learning the whole codebase.

Top-Level Files

Path Purpose
README.md Short project description and link to this documentation site.
mkdocs.yml Configuration for the documentation website.
.gitlab-ci.yml GitLab pipeline: compile checks and documentation deployment.
CMakeLists.txt Main build configuration for compiling the model.
runozflux Convenience script for building and running many OzFlux site simulations locally.
build_gadi Convenience script for compiling on Gadi with the expected module environment.

Documentation

Path Purpose
docs/ Source files for the documentation website.
docs/howto/ Practical setup, data access, running, and workflow guides.
docs/science/ Science and model-process notes.
docs/development/ Developer and project-organisation notes.
docs/img/ Images used by the documentation site.

Documentation pages are Markdown files (.md). After a documentation change is merged into lpjguess_dave, GitLab Pages rebuilds the published site automatically. See Contributing to the Documentation for the documentation workflow.

OzFlux Simulations

Most DAVE site-level work starts in:

benchmarks/ozflux/

Important files and directories:

Path Purpose
benchmarks/ozflux/<SiteName>/<SiteName>.ins Entry point for one site simulation.
benchmarks/ozflux/<SiteName>/gridlist.txt Longitude and latitude for that site.
benchmarks/ozflux/settings.ins Shared model switches and run settings for OzFlux simulations.
benchmarks/ozflux/outputs.ins Output file declarations. Comment or uncomment lines here to control outputs.
benchmarks/ozflux/pft_dave.ins DAVE PFT parameter definitions.
benchmarks/ozflux/soiln.ins Soil nitrogen settings.
benchmarks/ozflux/forcing/ Large forcing data downloaded separately from HIE-Storage.
benchmarks/ozflux/<SiteName>/out/ Default output directory created when a site is run.

For example, the Cumberland Plain run starts from:

benchmarks/ozflux/CumberlandPlain/CumberlandPlain.ins

That file sets the site-specific climate file and gridlist, then imports the shared OzFlux configuration files. OzFlux Site Simulations describes this input structure in more detail, while Running and Debugging via VSCode is the practical guide to running one site.

Source Code

Most model source code is C++.

Path Purpose
framework/ Core LPJ-GUESS framework: driver, data structures, parameters, output infrastructure, and utilities.
modules/ Process modules and DAVE-specific model code. This is where most scientific model changes happen.
modules/daveinput.cpp DAVE NetCDF input module, selected with -input nc.
modules/daveoutput.cpp DAVE output module and file_dave_* output definitions.
modules/davephotosynthesis.cpp DAVE photosynthesis calculations.
modules/growth.cpp Growth and allocation logic.
modules/soilwater.cpp, modules/hydraulics.cpp, modules/soil.cpp Water, hydraulics, and soil-related calculations.
libraries/ Small bundled support libraries used by the model.
command_line_version/ Command-line executable entry point.

For an overview of the DAVE NetCDF input settings, see Climate Input. The source code is not normally needed to run a site simulation, but this table can help locate the relevant area when discussing a model behaviour with a developer.

Build and Test Outputs

These are generated locally and normally should not be committed:

Path Purpose
build/ Local CMake build directory.
benchmarks/ozflux/<SiteName>/out/ Simulation outputs for a site.
benchmarks/ozflux/<SiteName>/state/ State files, if state saving is enabled.
tests/test_outputs/ Test output files generated by some test workflows.

If SourceTree or Git shows many files under build/, out/, or state/, do not commit them unless a maintainer has specifically asked for those files. See Common Failures for a short explanation of this common SourceTree situation.

Inputs and Outputs at a Glance

A typical local OzFlux run uses this chain:

benchmarks/ozflux/<SiteName>/<SiteName>.ins
    imports ../outputs.ins
    imports ../settings.ins
    imports ../soiln.ins
    reads   ../forcing/met/<SiteName>.nc
    reads   gridlist.txt
    writes  out/*.out

The model must usually be run from the site directory, for example:

cd benchmarks/ozflux/CumberlandPlain
../../../build/guess -input nc CumberlandPlain.ins

Running from the site directory matters because many paths in the instruction files are relative paths. Running Serially explains this convention and other command-line options; Debugging via VSCode covers the supplied graphical run configurations.
