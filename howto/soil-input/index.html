Soil Input

Soil input can be configured with named file blocks in an instruction file. Soil properties are read from plain text files.

Soil parameters can be specified in a few different ways:

Soil description Required file blocks Use when
Uniform texture with depth soildata Sand, clay, organic fraction and pH are available as one set of properties per location.
LPJ soil codes soilcode Locations are assigned one of the built-in LPJ soil classes.
Texture varying with depth soilclay and soilsand Sand and clay measurements are available for multiple depth intervals. Optional soilcoarse and soilph files add coarse fragments and pH.

Supply exactly one of these alternatives. soilclay and soilsand must always be supplied together; soilcoarse and soilph are only valid with that pair. Depth and slope can be fixed or read from separate files with any of the three descriptions.

A first example

Save these properties in soil.csv:

lon,lat,sand,clay,orgc,ph
150.75,-33.5,0.4,0.2,0.05,6.5

The model is flexible with regards to the exact format; you can use any delimiter you want, vertically-aligned columns, etc. See Plain Text Input Files for details. The model detects the delimiter and header, and maps the column names to the model's internal names.

Add the following to your simulation's instruction file, alongside its other settings:

file "soildata" (
    path "soil.csv"
    max_distance 0.1
)
hydrology "RICHARDS"
depth_soil 1500
slope 0

This supplies the same texture throughout a 1500 mm profile, with a slope of zero degrees. It covers simulation locations within 0.1 degrees of the table coordinate. The reader detects the comma separator and header. Column mappings connect the model's names, orgc and ph, to the file's names, orgC and pH.

path is mandatory in every file block. Relative paths start at the simulation's working directory, including when the block is in an imported instruction file. Absolute paths are also accepted. A later block with the same name replaces the whole earlier block, so repeat all options and mappings you still need.

Uniform texture with depth

Use file "soildata" for a single set of properties per location, applied throughout the soil profile.

Column Required? Units and behaviour
sand Yes Sand fraction, e.g. 0.4 for 40%.
clay Yes Clay fraction, e.g. 0.2 for 20%.
orgc Yes Organic material volume fraction, e.g. 0.05 for 5%.
ph Yes pH, e.g. 6.5.
soilc No Soil carbon content in kg C/m²; defaults to zero.
silt, cn, bulkdensity No Accepted and checked as numeric, but currently unused. Silt is calculated from sand and clay; supplied bulk density is not used by the model.

Sand, clay and organic content are fractions, not percentages.

If your column headers differ to those required, you can either change your file, or tell the model to use your column names with column blocks inside your file block. E.g.

lon,lat,sand,clay,orgC,phXYZ
150.75,-33.5,0.4,0.2,0.05,6.5

file "soildata" (
    path "soil.csv"
    column "orgc" (source "orgC")
    column "ph" (source "phXYZ")
)

Column names are case sensitive; therefore the mapping from orgC to orgc is important in this case.

For one uniform set of soil parameters applied to every gridcell, omit the coordinates and use one data row:

sand clay orgc ph
0.4 0.2 0.05 6.5

file "soildata" (
    path "uniform-soil.txt"
    domain "global"
)

LPJ soil codes

Use file "soilcode" for the built-in soil classes. The file must contain exactly one integer data column, apart from coordinates if present. Its header may have any name. Codes select predefined soil texture and physical properties:

Code Soil class
0 Ice (uses the coarse class properties)
1 Coarse
2 Medium
3 Fine
4 Medium-coarse
5 Fine-coarse
6 Fine-medium
7 Fine-medium-coarse
8 Organic
9 Vertisols

This input uses a default pH of 6.5, organic fraction of 0.05 and soil carbon content of zero.

A headerless coordinate/code table such as:

150.75 -33.5 2
151.00 -33.0 3

can be configured with:

file "soilcode" (
    path "soils_lpj.dat"
    domain "local"
    timestep "none"
    header "absent"
    max_distance 0.5
)

No column mapping is needed for the sole code column. If desired, explicitly map a headed column with column "soilcode" (source "class") when its header is class. To use one code everywhere, supply a headed global table with one data row, for example soilcode followed by 2 on the next line.

Texture varying with depth

Supply both file "soilclay" and file "soilsand". Each file needs a header whose data columns name contiguous depth intervals in centimetres, starting at the surface. For example, clay.txt could contain:

lon lat 0-20 20-60 60-100
150.75 -33.5 20 30 35

and sand.txt:

lon lat 0-20 20-60 60-100
150.75 -33.5 40 35 30

Configure them with:

file "soilclay" (path "clay.txt" max_distance 0.1)
file "soilsand" (path "sand.txt" max_distance 0.1)

Sand and clay values in these files are percentages, so 40 means 40%. This differs from the fractions used by soildata.

Optional files use the same layout:

File block Values Default when omitted
soilcoarse Coarse fragment percentages Zero
soilph pH for each interval 6.5 
file "soilcoarse" (path "coarse.txt" max_distance 0.1)
file "soilph" (path "ph.txt" max_distance 0.1)

All supplied layer files must describe the same depth intervals in the same order. Every data column must be a depth interval; use those names directly, without column "clay" or column "sand" mappings. Organic fraction defaults to 0.05 and soil carbon to zero throughout the profile.

The input intervals describe measured properties; they do not set total soil depth or the model's simulation layers. The model averages properties by overlap with its layers and extends the last interval's properties below the last supplied depth when necessary. Configure total depth separately below.

Soil depth and slope

Soil depth and/or slope can be fixed (same for all gridcells via a constant value in the instruction file) or dynamic (specified via an input file).

For Richards hydrology, the soil depth is clamped to 0.2–50 m and rounded to the nearest 100 mm. The instruction file parameter accepts 0–100000 mm, but values outside the model's depth limits are clamped. Slope values read from a map are clamped to 0–90 degrees.

Fixed Soil Depth and Slope

To fix the values to a constant, use the depth_soil and slope parameters. If depth_soil is set to zero, the model expects a depth map in file "soildepth". If slope is set to −1, the model expects a slope map in file "soilslope".

Variable Soil Depth and Slope

First, create a depth map depth.txt (again the exact format is flexible):

   lon    lat  depth
150.75  -33.5    1.5

and slope map slope.csv:

lon,lat,median
150.75,-33.5,4

These can be used alongside any soil description:

hydrology "RICHARDS"
depth_soil 0
slope -1
file "soildepth" (
    path "depth.txt"
    max_distance 0.1
)
file "soilslope" (
    path "slope.csv"
    column "slope" (source "median")
    max_distance 0.1
)

This selects 1.5 m depth and a 4 degree slope at the example location. A headerless depth map with rows such as 150.75 -33.5 1.5 instead needs to have its timestep and domain specified (as the model is unable to infer these without a header):

file "soildepth" (
    path "depth.dat"
    domain "local"
    timestep "none"
    header "absent"
    column "depth" (source "0")
    max_distance 0.1
)

File layout and location matching

All soil files use the reader described in Plain Text Input Files. That page documents delimiters, quoting, headers, missing values, and other options. For soil inputs specifically:

  • File block names and data column names are case sensitive. Structural headers such as lon/longitude and lat/latitude are case insensitive.
  • All files must be static. Omit timestep or set timestep "none"; annual and daily soil tables are rejected.
  • Longitude and latitude must be in degrees, with one row per coordinate. Use longitude in −180..180 and latitude in −90..90. Global tables may omit coordinates and have one data row applied to all gridcells.
  • A header normally lets the reader infer the domain. For headerless tables, specify header "absent", domain "local" or "global", and map numbered data columns as needed. Layer files always require headers.
  • Every local file independently selects the nearest coordinate within its own max_distance (in degrees). The default is 0, requiring an exact match. Set the radius on each file that needs a spatial tolerance, including depth, slope and optional layer files.
  • Distances are straight-line distances in longitude/latitude degrees, rather than kilometres. Longitude does not wrap at the date line. Equal distances select the smaller longitude, then the smaller latitude. Values are taken from the selected row without spatial interpolation.

The files can have different coordinate grids or mix global and local tables, but every active file must cover all requested simulation gridcells.

Migrating older configurations

The old file_soildata path and param "file_soil..." settings do not configure the current soil reader, but the files themselves are compatible with the new reader. Replace the old param-style parameters with the corresponding named file blocks. For example, replace file_soildata "soil.txt" with a file "soildata" block, adding mappings for headers such as orgC, pH, CN and soilC as needed.

searchstep_soil is retained for compatibility but does not control location matching in the soil input module. Replace its use with max_distance on each relevant file block.

Diagnosing errors

Files are parsed in full during initialisation, and active soil files are checked for spatial coverage of the gridlist. If initialisation fails:

  1. Read the error message
  2. Check that exactly one soil description is configured, including imported instruction files, and that any required depth or slope map is selected.
  3. Check column names and mappings, fraction versus percentage units, and metres versus millimetres for depth.
  4. For layer files, check that all depth headers are contiguous, start at zero and match across files.
  5. Check coordinates and each file's max_distance. Increase the radius only when using a more distant soil location is appropriate for the simulation.
  6. For parsing errors, follow Diagnosing errors in the plain text input guide.
